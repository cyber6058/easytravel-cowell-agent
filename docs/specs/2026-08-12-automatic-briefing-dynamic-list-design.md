# 新魅力說明會資料全自動流程與動態 LIST 版型設計

日期：2026-08-12
狀態：書面規格已於 2026-08-13 由使用者通過；0.2.0 實作計畫另行核准

## 1. 決策摘要

使用者平常只要提供下列任一來源，並要求「產生說明會資料」：

- 一個允許的新魅力行程網址；
- 一份本機行程 PDF；
- 同一產品的新魅力網址與 PDF。

系統就執行一次完整的本機 DRAFT 流程，目標產出 LIST 說明會 Word、逐頁 QA
檔及 Yating 語音檔。正常流程不再逐步詢問要使用哪一份 LIST 範本，也不再按
5／6／7 天選擇範本。

三份既有 LIST `.doc` 是一次性校準樣本，不是三個執行期選項。校準完成後，系統
只使用一份保存在私人本機設定區的 canonical LIST master，依來源中的實際天數
動態新增每日行程列。4 天、8 天以上及其他正整數天數都走同一套版型引擎。

若在維持已校準的最小可讀字級與表格規則下無法合理放入一頁，系統自動續頁，
並在每個續頁重複團體識別及每日行程欄位表頭。不得為了硬塞一頁而把文字縮到
不可讀，也不得截掉事實。

本規格在通過後取代既有設計中的下列限制：

1. 依 5／6／7 天選擇不同 LIST 範本；
2. LIST Word 必須固定單頁，超過一頁即阻擋；
3. 只測試或只支援 5／6／7 天。

來源優先、衝突阻擋、黃色 `待 OP 確認`、Yating-only、DRAFT／CONFIRMED、資料
保護及 LINE／發布邊界均維持不變。

## 2. 使用者操作契約

### 2.1 一句話啟動一次完整 DRAFT

當同一則要求同時包含來源及「產生說明會資料」的明確意圖時，該要求對該次
`draft_id` 授權以下動作：

1. 唯讀開啟使用者提供的本機 PDF；
2. 對使用者提供且通過 allowlist 的新魅力網址執行既有受限唯讀取得；
3. 唯讀載入已校準的私人 canonical LIST master；
4. 啟動本工具擁有且有時限的隱藏 Word COM instance；
5. 使用本機 `Microsoft Yating` 合成該次講稿；
6. 使用已設定的本機 `pdftoppm` 做逐頁 QA；
7. 若設定中已有可驗證的 ffmpeg 路徑，從已驗證 WAV 轉出 MP3。

這是單次、限於該來源與該 `draft_id` 的授權，不是永久授權，也不授權讀取其他
網址或檔案。來源或事實改變而形成新 `draft_id` 時，必須由新的產生要求重新啟動。

### 2.2 不包含在一句話授權內的動作

下列動作仍有各自邊界，不得隨 DRAFT 自動執行：

- 第一次 LIST 校準或校準規則變更；
- 尚未另行核准的正式 JMA 網路讀取；未取得時沿用既有「出發前更新」安全文字；
- 安裝、下載或搜尋 ffmpeg；
- 建立雲端 TTS 資源或呼叫 Azure／其他雲端語音；
- 把 DRAFT 升為 `CONFIRMED`；
- 傳 LINE、寄信、上傳、部署、發布或 push；
- 任何 Cowell 存取或寫入。

### 2.3 例外驅動互動

正常產出不逐步打斷使用者。只有下列情況才集中回報一次：

- 來源無法唯一辨識、無文字 PDF、網址不受允許或 parser 契約漂移；
- PDF 與官網對同一事實有阻擋衝突；
- 來源缺少會影響正確文件或講稿的必要事實；
- OP-only 欄位尚未確認；
- canonical master 缺少、遭修改或校準契約不符；
- 單一每日行程列即使續頁仍無法在最小可讀規格內完整呈現；
- Word、PDF／PNG QA、Yating、bookmark、WAV 或 MP3 驗證失敗；
- 外部或本機工具回傳未知結果。

可安全建立的部分產出仍保留。例如缺少 ffmpeg 時，Word、PDF／PNG、WAV、TXT、
SRT 仍可完成，只把 MP3 標為未完成；Yating 失敗時仍保留 Word、逐字稿及錯誤報告。

## 3. 來源與事實處理

來源解析及合併沿用既有契約：

- 同一行程的 PDF 事實優先於官網；
- 官網供應仍有效的現行公告；
- 未知 OP 資料維持黃色 `待 OP 確認`，不得猜值；
- 日期、航班、飯店、天數或每日行程的實質矛盾會阻擋正式產出；
- URL+PDF 必須能證明是同一產品，否則停止合併；
- 掃描型無文字 PDF 明確回報 `PDF_OCR_REQUIRED`，不暗中 OCR；
- 完整來源內容只存在當次暫存區，manifest 只留必要證據、時間及雜湊。

每日行程必須是從 1 開始、無重複且連續的完整序列。文件天數直接取自已驗證的
來源資料，不從檔名、產品代碼或現有範本天數猜測。

## 4. 一次性 LIST 格式校準

### 4.1 校準目的

三份使用者提供的 LIST 文件只用來證明哪些部分是固定格式、哪些部分只是行程
天數或內容造成的變化。校準不修改原檔，也不把原檔、完整文字、QR 圖或衍生
DOCX 提交到 Git。

校準前後都計算三份原檔 SHA-256；結束時必須完全一致。校準程序用受限 Word COM
逐一取得並比對：

- 紙張、方向、邊界、section、header 及 footer；
- 固定標題、欄位錨點、段落樣式、字型、字級與間距；
- 表格順序、合併格、欄寬、框線、底色及對齊；
- 一般資料、航班、每日行程、領隊／緊急資訊等區塊；
- 每日行程表頭及一列可複製的 body-row 原型；
- QR／圖片 shape 的位置、大小與錨定方式；
- 頁面分隔、列是否可跨頁及表頭重複行為。

校準時把每日行程列數、行程文字、日期、團務值，以及可證明是隨內容量調整的
列高／段落間距／字級視為可變資料。這些自適應差異要轉成有上下限的排版規則，
不是轉成另一份天數範本。其餘結構若三份樣本無法歸一成同一契約，校準就 fail
closed，列出精確差異，不投票、不平均，也不自行挑一份當作正確答案。

### 4.2 canonical master 的建立

三份樣本通過共同契約後，校準程序採下列固定方式建立 master，不要求使用者選擇：

1. 以通過契約且天數為三份樣本中位數的文件作為結構基底；若天數同值，使用
   SHA-256 字典序最小者，讓結果可重現；
2. 複製到新的私人校準目錄，絕不覆寫來源檔；
3. 保留固定 shell、樣式、表格、合併格、QR 及 shape；
4. 清除行程／團務值，將每日區塊正規化為一列表頭與一列 body-row 原型；
5. 建立 schema-versioned 私人 calibration manifest，記錄三份來源雜湊、共同
   結構契約、master 雜湊、可讀性下限及校準程式版本；
6. 重新以 Word 匯出 PDF／PNG，確認 master 仍可開啟且固定視覺元素完整。

canonical master 與 calibration manifest 放在使用者私人本機設定區並由 config
指向；兩者皆不得進 Git。repo 只保存通用校準與動態排版程式，不保存來源內容、
QR 或可還原私人範本的資料。

### 4.3 執行期契約

每次產出只接受 config 指向的唯一 canonical master，不接受 template list，也沒有
5／6／7 天 selector。執行前驗證：

- master SHA-256 與 calibration manifest 相符；
- calibration schema 與 generator 支援；
- 固定錨點、表格、合併格、QR／shape 及頁面設定仍符合契約；
- master 不是來源 PDF、產出檔或 Git 追蹤檔。

任一項不符都停止 Word 產出並要求重新校準，不退回舊的按天數選範本行為。

## 5. 動態天數與自動分頁

### 5.1 同一版型處理所有天數

動態引擎從 canonical master 的 body-row 原型複製實際需要的 N 列，N 是來源中已
驗證的正整數天數。程式不得維護 `if day_count in {5, 6, 7}` 之類分支。

每一列保留日期、行程、飯店、餐食及既有固定欄位。日期只能使用來源明示日期，
或在首日日期與完整連續天數都已確認時做可驗證的逐日加一；若來源日期與推導
結果衝突，必須阻擋。

顯示文字可使用既有、固定且可測試的安全縮寫規則，但完整來源文字仍保存在
manifest／review。縮寫不得移除時間、集合資訊、地點、交通、安全提醒或其他會
改變意思的事實。

### 5.2 版面決策不以天數硬編碼

引擎先用校準所得字級、間距、欄寬及列規則建立 Word，再由 Word 實際 layout
結果決定頁數。不是「8 天固定兩頁」，也不是「7 天一定一頁」。內容長度與可讀性
共同決定是否續頁。

排版優先順序固定為：

1. 使用校準的正常字級與間距；
2. 套用已核准的顯示用安全縮寫；
3. 在不低於三份樣本共同最小可讀字級、不縮窄固定欄位的前提下調整；
4. 若仍無法合理容納，自動續頁。

不得透過低於可讀性下限、隱藏文字、裁切、縮放整頁或刪除事實來維持單頁。

### 5.3 續頁規則

- 第一頁保留既有固定抬頭、QR、一般資料及航班區塊；
- 每個續頁都必須顯示團體編號／團體名稱，以及每日行程的欄位表頭；
- 每日行程列不得拆成上下兩頁；
- 每日行程依日次連續排列，不得重複、遺漏或重新排序；
- 領隊／緊急資訊等結尾區塊放在最後一頁；
- QR 只保留在第一頁，除非三份樣本的共同契約證明它原本就是重複 header；
- 續頁沿用 master 的字型、框線、底色與欄寬，不建立另一套「長天數版型」。

若單一日的內容在安全縮寫後仍高於一整個可用頁面，系統阻擋 Word 並指出日次與
超出的欄位；不得把同一日切開或默默刪字。

## 6. 自動產出流程

一次正常 DRAFT 執行依序完成：

1. 正規化 URL／PDF 輸入並建立來源雜湊；
2. 執行受限來源讀取、parser 與產品唯一性判斷；
3. 依既有優先規則合併事實，建立 blocking conflicts、warnings 及 OP fields；
4. 建立 immutable manifest 與 `draft_id`；
5. 產生 LIST patch plan，從唯一 master 動態建立 N 天表格與續頁；
6. 建立八段 narration input，交由 agent 產生講稿，再執行事實與數字驗證；
7. 以本工具擁有的 Word COM instance 產生 DRAFT DOCX、PDF 及逐頁 PNG；
8. 以 Yating 單次連續合成 WAV，以真實 bookmarks 建立 SRT，並寫出 TXT；
9. 有既有 ffmpeg 設定時，從通過驗證的 WAV 轉出 MP3；
10. 驗證所有 artifact hash、頁數、文字、QR、WAV header、bookmark 與時間軸；
11. 寫出 review，集中回報完成項目、缺漏項目及唯一需要使用者處理的例外。

Word 與 Yating 可以在資料、講稿均已凍結後執行，但不得讓兩者使用不同的
`draft_id` 或不同講稿。未知 Word／Yating／ffmpeg 結果不自動重試；先檢查本次
owned temporary output，再 fail closed。

## 7. 產出與狀態

每次產出仍位於 Git 忽略的：

`output/briefings/<product-code>/<timestamp>/`

完整 DRAFT 目錄預期包含：

- `DRAFT_<product-code>_說明會資料.docx`
- `qa/DRAFT_<product-code>_說明會資料.pdf`
- `qa/page-001.png` 至 `qa/page-NNN.png`
- `DRAFT_<product-code>_說明會語音.wav`
- `DRAFT_<product-code>_說明會語音.mp3`（僅在既有 ffmpeg 可用且驗證通過時）
- `DRAFT_<product-code>_逐字稿.txt`
- `DRAFT_<product-code>_字幕.srt`
- `review.md`
- `manifest.json`

狀態定義維持：

- `DRAFT_READY`：可供審核，可能仍有黃色 OP 欄位或非阻擋警告；
- `BLOCKED`：存在來源衝突、必要事實缺漏或必要 artifact QA 失敗；
- `CONFIRMED`：零阻擋、零必要黃色欄位、Word 與音訊 QA 通過，且使用者對精確
  `draft_id` 明確確認。

自動流程只做到 DRAFT。`CONFIRMED` 仍需使用者對畫面列出的精確 `draft_id` 明確
確認；確認只提升同一批已驗證檔案，不重新抓來源、不重新 render，也不傳 LINE。

## 8. QA 與驗收標準

### 8.1 校準驗收

1. 三份來源文件校準前後 SHA-256 完全相同；
2. 三份文件都能以受限 Word COM inspect 並各自匯出 PDF／PNG；
3. 共同固定契約有機器可讀的校準報告；日數、行程／團務內容及可證明的自適應
   版面差異都有明確規則，不殘留按天數選範本的分支；
4. canonical master 可從私人設定路徑重新載入，hash 與 manifest 相符；
5. 原始 `.doc`、canonical master、calibration manifest、PDF／PNG 均未被 Git 追蹤；
6. 人工逐頁確認抬頭、QR、表格、合併格、框線、字級及欄寬與來源格式一致。

若第 3 項不成立，校準狀態是 `BLOCKED`，不得宣稱已抓出固定格式。

### 8.2 動態版型驗收

以去識別 synthetic 行程至少驗證 4、5、6、7、8、12 天：

- 4／5／6／7 天案例在內容量相當時維持既有可讀 A4 外觀；
- 5／6／7 天另與三份校準樣本逐頁人工比對；
- 8／12 天 fixture 刻意放入足以觸發續頁的內容，確認自動分頁；
- 所有頁面的團體識別、每日表頭、日次連續性及最後資訊區塊正確；
- 每日列不跨頁，沒有文字裁切、重疊、空白假成功或低於校準字級下限；
- 一個單日內容過長 fixture 必須 fail closed 並指出日次，不得截字；
- Word 報告的頁數、PDF 頁數與 PNG 數量完全一致；
- QA 檢查每頁 A4、文字非空、必要欄位、QR 第一頁存在及 artifact hash。

### 8.3 端對端驗收

- URL-only、PDF-only、URL+PDF 各至少一例；
- 正常案例只需一次產生要求，不出現範本選擇問題；
- 缺值與衝突集中成一次例外報告；
- Yating WAV／TXT／SRT 內容、hash 與時間軸一致；
- 有既有 ffmpeg 時 MP3 可解碼，沒有時不安裝且清楚標示缺少；
- 一個 `BLOCKED` DRAFT 與一個經精確 `draft_id` 核准的本機 `CONFIRMED`；
- 完整離線測試、opt-in Word／Yating integration、視覺檢查、artifact／PII／secret
  scan 與 `git diff --check` 全部通過；
- 未實際執行的網路、JMA、Word、音訊或 MP3 項目必須明示「未驗證」。

## 9. 實作方向與版本邊界

採用「私人 canonical master + 動態 row／pagination engine」；不採用下列方案：

- 執行時依天數挑三份範本：無法涵蓋 4 天及 8 天以上，也會把未來每個天數變成
  新選項；
- 從空白 DOCX 重建相似文件：容易遺失既有 merged cells、QR、shape、樣式與 Word
  特有版面；
- 硬塞單頁：會犧牲可讀性或內容完整性。

這是既有 0.1.0 Word 契約的行為變更，下一版以 0.2.0 規劃。舊 config 若只指向
未校準的單一來源 `.doc` 或舊 layout fingerprint，必須顯示可操作的重新校準訊息，
不得靜默套用或自動挑另一份檔案。

正式實作前先建立逐檔案、逐測試、逐 commit 的執行計畫。第一次實際讀取三份
私有範本、啟動 Word COM 並產生校準檔，仍是該計畫中的獨立明確關卡；本設計文件
本身不執行該關卡。

## 10. 完成定義

本功能只有在以下條件同時成立時才可稱為完成：

1. 三份樣本已實際校準，來源 hash 不變，固定格式已由機器報告與人工視覺驗證；
2. 執行期只存在一份 canonical master，沒有 5／6／7 天選擇邏輯；
3. 4、5、6、7、8、12 天動態版型及續頁測試均通過；
4. 使用者提供 URL／PDF 並下達一次產生要求，即得到可審核的安全 DRAFT 或一份
   集中的可操作例外報告；
5. Word／PDF／PNG、WAV／TXT／SRT，以及可用時的 MP3 都有實際 QA 證據；
6. CONFIRMED、LINE、上傳、部署與發布沒有被 DRAFT 流程暗中執行；
7. 完整測試實際執行且看到輸出，所有未驗證項目如實標示。
