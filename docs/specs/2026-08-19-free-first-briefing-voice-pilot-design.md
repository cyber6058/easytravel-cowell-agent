# 免費優先的說明會本人語音試驗設計

日期：2026-08-19
狀態：書面規格與 5 至 10 秒 reference 修正已核准；Gate I 離線安全骨架已完成
性質：隔離式試驗設計，不是安裝、下載、訓練、上傳或正式管線實作授權

## 背景與問題

目前說明會旁白由本機 `Microsoft Yating` 產生。技術檢查可確認 WAV、TXT、SRT
及時間軸一致，但使用者實際聽感有兩個系統性問題：

- **A：整篇語調太平**，每句的重音、情緒與資訊層級近似；
- **B：句子交界生硬**，聽起來像許多小音檔拼接，而不是同一個人連續說明。

使用者提供一段本人影片作為可行性樣本：

`C:\Users\cance\Downloads\5fbafd89-d770-4af1-9e87-23a72e7d254f.mp4`

本機只讀前檢結果如下：

- 檔案大小 `49,448,275` bytes，長度約 `178.84` 秒；
- H.264 影片、AAC 立體聲 `44.1 kHz`；
- 音訊 RMS 約 `-26.12 dBFS`、peak 約 `-5.12 dBFS`，未偵測到 clipping；
- 本機語音辨識判定為中文，約 60 個語音段、822 個不含空白字元；
- 使用者確認片中只有本人聲音，沒有背景音樂或其他說話者。

這些數字只證明樣本具備試驗價值，不等同於真人聽感、錄音室品質或語音複製
效果已通過。影片原檔保持不變，也不得加入 Git。

## 目標

1. 先以零付費、本機執行的方式，判斷本人聲音複製是否明顯優於 Yating。
2. 對 A 問題加入段落角色、資訊重音與自然轉場，而不改變任何旅遊事實。
3. 對 B 問題改用語意完整的長段落，避免把每一句各自合成後直接串接。
4. 以固定盲測與明確門檻決定繼續、換模型或停止，不以「感覺好像有改善」放行。
5. 只有短試驗通過後，才討論 30 至 60 分鐘錄音資料及 5 至 7 分鐘長稿。

使用者指定的目標說話風格是：

> 本人對一小群旅客自然說明：親切、清楚、不播音、不亢奮。

## 非目標

本設計不包含：

- 修改目前 `src/travel_briefing/` 的 Yating 正式產生流程；
- 把語音複製結果標成 `CONFIRMED` 或交付旅客；
- 安裝 SmartSub、ZipVoice、GPT-SoVITS 或任何新依賴；
- 下載模型、權重、Windows portable package 或額外執行環境；
- 上傳影片、聲音、逐字稿或其他檔案；
- 使用雲端 TTS、付費 API、訂閱額度、信用卡或自動加值；
- 建立虛擬人、嘴型同步影片、LINE 傳送、發布或部署；
- 宣稱 2 分 59 秒樣本已足以訓練正式模型；
- 將 ChatGPT／Codex 訂閱額度視為第三方 GitHub 語音工具可用的 API 額度。

上述任何一項若未來需要執行，都必須有新的明確授權；下載依賴與模型本身也是
獨立關卡，不因核准此規格而自動成立。

## 已考慮方案

### 1. SmartSub 搭配 ZipVoice（選定的第一順位）

以 [SmartSub](https://github.com/buxuku/SmartSub) 的 Windows 圖形介面使用
[ZipVoice](https://github.com/k2-fsa/ZipVoice) 本機零樣本語音複製。這條路徑不需
API key、沒有按次付費，且最符合目前只有 Intel 內顯、8 GB RAM 的機器。

限制是這台機器沒有 NVIDIA GPU；能否在 Intel CPU／Vulkan 路徑上以可接受速度
完成，必須用實機證據判定，不能先承諾。短參考音訊與精確逐字稿的品質也會直接
影響結果。

### 2. GPT-SoVITS（免費備援）

若第一順位沒有達到聲音相似度或自然度門檻，再評估
[GPT-SoVITS](https://github.com/RVC-Boss/GPT-SoVITS)。它可做零樣本試驗，也較適合
後續用較長資料微調，但安裝複雜度、CPU 時間與記憶體風險較高，因此不與第一順位
同時安裝。

### 3. 付費雲端服務（最後順位）

只有兩個免費方案均無法達標時，才另行比較 ElevenLabs 或其他合法的付費服務。
屆時必須重新確認價格、台灣中文品質、聲音同意機制、資料保存／刪除政策、商用
權利及實際上傳內容；採單月、禁止自動加值，且付款與上傳各自取得當次確認。

### 4. 維持 Yating 並只改拼接

這可降低 B 的部分症狀，但無法合理期待解決 A，也不會得到本人聲線。因此保留
Yating 作為盲測基準，不把它當成這次自然度改善的主要方案。

## 選定策略

依序執行，不平行安裝多套工具：

1. SmartSub + ZipVoice 的完全本機短試驗；
2. 第一順位失敗且使用者同意後，才規劃 GPT-SoVITS 的完全本機短試驗；
3. 兩者均未過門檻，才提出付費雲端比較與獨立授權；
4. 任一路徑通過短試驗後，才進入長資料與長稿階段。

「免費」指不發生按字、按秒或 API 費用；仍可能需要下載數 GB 的程式／模型、
占用磁碟與長時間 CPU。實作前必須重新核對實際下載大小、模型權重來源及授權。
SmartSub 程式碼、ZipVoice 程式碼與實際散布權重的授權要分開檢查，不能只看 repo
首頁就推定所有檔案都可用於正式商業產出。

## 隔離邊界

未來的短試驗只能是旁路 proof-of-concept：

- 試驗程式預定放在 `scripts/voice_pilot/`；
- 試驗輸出預定放在 Git 已忽略的 `output/voice-pilot/`；
- 原始影片、抽出的參考音訊、逐字稿、模型 cache、WAV／MP3 及評分表中的私人內容
  均不得提交 Git；
- 不修改 `src/travel_briefing/`、正式 CLI、Skill、package、Yating provider、
  `BriefingDraft` schema 或現有 DRAFT；
- 不讀取 Cowell、不執行 NewAmazing GET、不啟動 Word、不查 JMA、不呼叫 LINE；
- 不覆蓋原始影片或任何既有 briefing artifact。

實作計畫若發現現有 `.gitignore` 無法完整攔住模型或私人媒體，必須先加入精確的
忽略規則與洩漏測試，再接觸檔案；不能依賴操作者記得不要 `git add`。

## 元件與資料流

短試驗的概念資料流為：

`原始影片（唯讀） -> 本機抽音 -> 參考片段前檢 -> 固定測試稿 -> ZipVoice -> 音訊正規化 -> 盲測包`

### `ReferenceAudioPreflight`

- 從原始影片本機抽出單聲道 WAV 工作副本，不改原檔；
- 從本人連續發言中選一段 5 至 10 秒、語氣自然且語意完整的乾淨片段；
- 排除碰撞聲、明顯呼吸、句首被切、句尾被切、爆音、旁人聲音及背景音樂；
- 排除旅客或第三人的姓名、電話、證件、訂單與其他不必要的敏感內容；
- 為參考片段建立逐字精確 transcript，標點可供模型斷句，但字詞不得靠猜測；
- 保存來源時間範圍、音訊規格與 SHA-256，讓比較可以重現；
- 自動檢查只判斷技術條件；使用者仍需確認片段確實是本人且文字正確。

第一輪只固定使用一個參考片段。不能試十幾個片段後只挑最好聽的一個而不揭露，
因為那會讓短試驗結果被挑選偏誤放大。

### `SpokenScriptDirector`

固定測試稿長度為 60 至 90 秒，內容取自既有本機 canonical 說明會文字，但不得含
旅客個資、未確認 OP 欄位、爭議事實或影片樣本中已讀過的相同句子。Yating 與
ZipVoice 必須使用完全相同的字詞。

在不改事實的前提下，測試稿明確標記四種段落功能：

1. 開場：像本人開始對旅客說明，不用播報腔；
2. 重點提醒：適度放慢或加重資訊重心，但不亢奮；
3. 轉場：讓前後資訊有連續關係，不逐句重設語氣；
4. 收尾：自然結束，不用廣告式升調。

角色標記是合成控制資料，不得朗讀出來，也不得為了表現力新增來源不存在的承諾、
警告、日期、金額、班號或其他事實。

adapter 只能把角色映射到候選引擎確實支援且已驗證的控制。如果 ZipVoice 沒有對應
的 style control，就只靠連續上下文、口語化但事實不變的文字與標點來測試；不得
把未支援的角色文字送入 TTS，也不得宣稱模型接受了其實不存在的情緒指令。

### `SemanticChunker`

正式方向以每個約 20 至 45 秒的語意段落為單位，只能在章節轉換或自然呼吸點切分。
不得按字幕句子、固定字數或任意 PCM 大小切分。短試驗應使用 ZipVoice 原生的長文
處理路徑作為一個邏輯合成工作；若引擎內部依標點分塊，必須保留其邊界證據並在
盲測中特別檢查，不得把內部拼接隱藏成「整篇一次完成」。

### `AudioAssembler`

- 只接受規格一致、可解碼且非靜音的完整語意段；
- 統一聲道、取樣率與目標 loudness 後再比較；
- 段落間只放自然且有上限的停頓，不裁掉正常尾韻；
- 禁止直接把許多逐句 raw PCM 無交叉檢查地串接；
- 記錄每個輸入段、邊界、停頓值、輸出時長與 SHA-256；
- 不以背景音樂掩蓋接縫。

### `FinalAudioAligner`

字幕時間必須從最終組裝後的音訊重新對齊，不能沿用模型預估秒數或組裝前時間。
測試階段可以沒有可交付 SRT；進入 5 至 7 分鐘長稿前，必須有可重現的 alignment
方法，且關鍵名稱、數字與每個接縫均通過人工檢查。

## 關卡 0：安裝前證據與授權

書面規格通過後，實作計畫首先只做安裝前清單，至少列出：

- SmartSub release／commit、ZipVoice／權重版本與直接來源；
- 程式碼及每份權重的 license；
- 預估下載量、解壓後磁碟量、RAM／CPU 路徑及是否需要系統管理員權限；
- 安裝目標與 model cache 的絕對路徑；
- 完整移除／回復方式；
- 是否會建立網路服務、遙測、登入、API key 或對外連線；
- SHA-256 或上游可驗證的 release 完整性資訊。

只有使用者另行同意此精確清單後，才可下載或安裝。若下載來源、權重授權或實際
需求與清單不符，立即停止，不換鏡像、不改裝其他版本。

## 關卡 1：60 至 90 秒盲測

### 控制條件

- 同一份固定稿；
- 同一個目標 loudness，禁止以「比較大聲」冒充比較自然；
- Yating 為現況基準，ZipVoice 為候選；
- 輸出隨機標成 A／B，評分前不揭露引擎；
- 評估開場、重點提醒／轉場、收尾三個預先固定片段，不事後挑片段；
- 使用者以耳機或平常播放設備完成一次主要評分。

### 評分尺度

- `1`：明顯機器或無法接受；
- `2`：問題頻繁，不能用於旅客說明；
- `3`：可理解但仍明顯不自然；
- `4`：自然、可長時間聽，只有小瑕疵；
- `5`：接近本人自然說明。

### 通過條件

ZipVoice 必須同時達成：

1. 整體自然度至少 `4/5`；
2. 三個預先固定片段中至少兩個在自然度上勝過 Yating；
3. 本人聲音相似度至少 `3/5`；
4. 開場、重點、轉場及收尾沒有相同語調反覆重設的 A 問題；
5. 所有模型內部與外部接縫均無明顯跳音、截尾或不自然空白；
6. 人名、地名、日期、時間、班號、金額與安全指示若出現在測試稿，必須 100%
   正確，不能只靠字幕才理解；
7. 音檔可解碼、非靜音，且 manifest 的稿件、版本、時長與 hashes 完整。

第一次未通過時，只允許一次事先記錄的單一設定調整，例如更換一個已確認的乾淨
參考片段或調整一項推論參數；不能同時換稿、換片段、換模型與後製。第二次仍未
通過就停止 ZipVoice 路徑，保留誠實結果，再由使用者決定是否規劃 GPT-SoVITS。

## 關卡 2：長資料與 5 至 7 分鐘驗證

只有關卡 1 通過，才建立 30 至 60 分鐘錄音腳本與錄音規範。這批資料的用途必須
先說清楚：零樣本 prompt 素材庫與模型微調資料是不同用途，不能把「錄很多次」
自動描述成模型已受訓。若選定模型／硬體不能合理微調，應先揭露，再決定是否值得
錄製完整資料。

長資料應包含自然開場、一般敘述、數字／日期／班號／金額、地名、提醒、轉場及
收尾；保持同一人、同一麥克風距離、安靜環境與正常語速。原音與逐字稿逐段配對，
錯讀不可只改 transcript 掩蓋。

長稿驗收使用一份 5 至 7 分鐘真實說明會稿，並同時要求：

- 關卡 1 的所有品質條件持續成立；
- 每一個語意段落與每一個組裝接縫逐一人工聽過；
- 關鍵名稱、數字與安全資訊 100% 正確；
- 沒有音色漂移、速度突然改變、尾音截斷、重複字或異常長停頓；
- 最終音訊與字幕逐段核對，邊界漂移不超過 `0.5` 秒；
- 產出時長、模型／權重版本、prompt、參數、段落及 hashes 可重現；
- 使用者明確判定這版可取代 Yating，否則正式流程不變。

長稿通過仍只證明候選音訊品質，不自動授權整合、CONFIRMED 或傳給旅客。

## 失敗、安全與資料處理

- 原始影片永遠唯讀；抽音與切片只建立新檔。
- 有他人聲音、背景音樂、逐字稿不確定或片段界線不完整時，不送模型。
- 本機執行逾時或失敗時，先檢查程序與既有輸出；不把半成品當成功。
- 未知結果的雲端請求不得自動重送；先確認供應商狀態、帳務及既有 job。
- 不自動下載另一份權重、不換非官方鏡像、不關閉安全防護以求成功。
- 不以降噪、混響、音樂或激進裁切掩蓋原始聲音／接縫問題。
- 不保存或提交完整語音辨識逐字稿到 Git；manifest 只留必要技術證據與去識別資訊。
- 若採雲端，影片不出機；只考慮上傳最小必要音訊及其精確文字，且需另行授權。
- 任何付費試驗均採固定小額、單月、無自動續費／加值；實際付款前再次確認。

## 驗證與證據

未來實作至少要留下下列可核對結果，而非只回報「聽起來比較好」：

- 原始檔、抽音、prompt、固定稿、A／B 音檔及最終音檔的 SHA-256；
- 工具、模型、權重、推論參數、硬體路徑與耗時；
- 音訊聲道、取樣率、位元深度、時長、peak、RMS／loudness、非靜音檢查；
- 所有模型內部分塊、外部語意段與組裝接縫的時間位置；
- 盲測隨機對照表，在評分完成前保持封存；
- 使用者逐項分數、關鍵詞錯誤與通過／停止判定；
- 任何調整的唯一變數及調整前後結果。

自動檢查只能證明檔案結構與資料一致。A、B、本人相似度及能否用於旅客說明，
必須由使用者實際聽過才可宣稱通過。

## 未來正式整合邊界

候選模型通過兩個關卡後，仍需另一份正式整合設計，至少處理：

- `VoiceProvider` 介面與 Yating／本人聲音的明確選擇，不得無聲 fallback；
- 20 至 45 秒語意段落契約及跨段音色一致性；
- 最終音訊 forced alignment 與 SRT 產生；
- pronunciation review、關鍵事實驗證、失敗狀態與 DRAFT／CONFIRMED 規則；
- model／prompt／聲音同意紀錄、離線 package 與不同機器的可重現性；
- 模型及權重的商用授權與後續升級策略；
- 專案 `AGENTS.md` 中目前「不得使用 cloud TTS／upload」邊界是否需要精確修訂。

在整合設計、實作計畫、測試與人工驗收全部通過以前，Yating 仍是正式流程唯一
已核准 provider；試驗結果不得被正式 workflow 自動選用。
