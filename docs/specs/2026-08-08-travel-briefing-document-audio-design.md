# 旅遊產品說明會 Word 與語音產生器設計

日期：2026-08-08
更新：2026-08-09（本機語音試聽決策）
狀態：原設計已由使用者逐段確認；Yating 修訂待使用者書面審閱

## 成果

在 Codex 或 Claude 的對話式 Skill 中，OP 每次提供一個新魅力旅遊產品網址、
一份產品 PDF，或兩者同時提供。系統建立可審核的結構化草稿，再產出：

- 沿用既有 LIST 版面的 Word 說明會資料；
- 適合由 OP 手動傳到 LINE 的繁體中文 MP3；
- 供未來嘴型同步使用、且與 MP3 內容相同的 WAV；
- 完整逐字稿與 SRT 字幕；以及
- 一份列出來源、缺漏、衝突、天氣查詢時間與產出狀態的審核報告。

第一階段只支援新魅力旅遊的大阪、東北與北海道產品。每次只處理一個產品，
不需要另外購買 LLM API 額度：對話中的 Codex／Claude 負責理解資料與撰寫口語稿，
本機程式負責可重複驗證的解析、版面套用、語音合成與檔案檢查。

## 2026-08-09 本機語音決策

使用者以同一份 105 字合成稿比較 Hanhan 與 Yating，判定 Yating 較好，並表示
目前沒有 Azure Speech 資源。方案比較與決定如下：

1. **Yating 整篇連續合成，缺少即阻擋（採用）**：聲音已通過方向試聽，不需要
   雲端資源；以零時長 SSML bookmarks 建立字幕時間，可保留連續韻律並 fail closed。
2. **Yating 按字幕逐段合成，或缺少時自動退回 Hanhan（不採用）**：實作可沿用
   現有分段 WAV 管線，但可能重現停頓感，而且 Hanhan 已未通過人工試聽。
3. **Azure HsiaoChen（延後）**：可能提供神經語音，但需要另一個外部資源與核准；
   第一階段已有通過方向試聽的本機選項，因此不建立、不設定也不呼叫 Azure。

這項決定只改變說明會語音模組，不擴張 Cowell、LINE、影片或其他外部整合範圍。

## 第一階段範圍

### 包含

- 接受產品頁 URL、PDF 路徑，或兩者並用。
- URL 或 PDF 單獨存在時仍可建立草稿。
- PDF 內含產品代碼時，自動嘗試解析對應的新魅力產品頁。
- 產生 5、6、7 天 LIST Word 草稿。
- 擷取最新版「其他說明」，並改寫成約 6 至 8 分鐘的口語稿。
- 在可靠預報範圍內加入每天主要住宿城市的即時短期預報。
- 本機 `Microsoft Yating` 台灣女聲為唯一自動 TTS；缺少該聲音時阻擋音訊，
  不自動改用其他聲音。
- 所有產出先經 OP 審核，再由 OP 手動傳送 LINE。

### 不包含

- 自動傳送 LINE、建立 LINE Bot 或管理旅客名單。
- 建立、設定或呼叫 Azure Speech；未來若要加入雲端 TTS，必須另行設計與核准。
- 真人或 AI 虛擬人影片；WAV 與 SRT 只為後續階段預留。
- 批次處理、排程、獨立後台網站或多人權限系統。
- 新魅力旅遊以外的產品來源，或大阪、東北、北海道以外的區域。
- 猜測集合資料、領隊資料、飯店、天氣或任何來源沒有提供的事實。

上述非範圍項目需要各自的新設計與核准，不能由本功能自動擴張。

## OP 操作流程

1. OP 在對話中貼產品 URL、PDF 路徑，或兩者。
2. Skill 先做輸入辨識、資料擷取與正規化，不立即產生正式檔。
3. 驗證器建立缺漏與衝突清單，並決定 `DRAFT_READY` 或 `BLOCKED`。
4. 在可安全產生的範圍內輸出 DRAFT Word、語音、逐字稿、SRT 與審核報告。
5. OP 以對話補充黃色欄位，並對每個阻擋衝突指定採用值。
6. 系統以同一份結構化資料重新驗證及產生草稿。
7. 只有 OP 明確確認後，狀態才可改為 `CONFIRMED`，並產生不含 DRAFT
   檔名前綴及黃色待確認欄位的正式檔。
8. OP 自行把確認後的 MP3 或其他檔案傳到 LINE。

正式確認只改變本機產出狀態，不授權自動傳訊、上傳或其他對外發布。

## 架構與模組邊界

整體資料流為：

`URL／PDF -> 擷取器 -> BriefingDraft -> 驗證器 -> Word／講稿 -> TTS -> QA -> 產出資料夾`

模組保持下列單一職責：

1. **輸入解析器**：驗證 URL 網域與 PDF 路徑，計算來源檔雜湊，不修改來源。
2. **新魅力頁面擷取器**：解析產品識別、航班、每日行程、住宿及「其他說明」。
3. **PDF 行程擷取器**：抽取日期、航班、每日景點、餐食及住宿，保留頁碼證據。
4. **產品頁解析器**：由 PDF 的產品代碼建立或查找唯一產品頁；多個候選必須阻擋。
5. **資料正規化器**：把不同來源轉成同一份 `BriefingDraft`，不在此決定衝突。
6. **來源與衝突驗證器**：依核准的優先規則選值，產生阻擋項目及提醒。
7. **天氣介面**：把主要住宿城市解析成官方預報區，取得有時效的每日預報。
8. **LIST Word 產生器**：只修補已確認範本；不重建近似版面。
9. **口語稿產生器**：依結構化通知項目產生口語稿，並用必要內容清單驗證。
10. **TTS 介面**：以 Windows Media Speech 的 `Microsoft Yating` 整篇連續合成，
    並用 SSML bookmark markers 取得句段時間；缺少 Yating 或 marker 不一致時
    fail closed。
11. **產出驗證器**：檢查 Word 版面、音檔、字幕、來源記錄與敏感檔案邊界。

每個模組只能透過明確的結構化資料交換；HTML、PDF 原文、Word COM 物件或
Windows 語音物件不得滲入其他模組。

實作放在獨立的 `src/travel_briefing/` 套件，不能依賴或改變既有 Cowell
登入、護照、名單與分房模組。另建立 `easytravel-briefing-materials` 操作 Skill；
Codex 與 Claude 的薄包裝都呼叫同一套 CLI 與資料契約。既有全域
`briefing-material-builder` 的範本契約與修補流程作為已驗證基礎，移入或包裝成
repo 可測試的單一實作，不能同時維護兩份會逐漸分歧的 Word 修補器，也不能在
執行時硬編碼依賴使用者 home 目錄下的個人 Skill 路徑。

## 統一資料契約

`BriefingDraft` 至少包含以下欄位群組：

- `draft_id`：由產品代碼、來源雜湊與產生時間建立的唯一草稿識別。
- `status`：`DRAFT_READY`、`BLOCKED` 或 `CONFIRMED`。
- `product`：產品代碼、名稱、區域、天數、出發日及回程日。
- `sources`：來源種類、原始位置、雜湊、擷取時間及解析器版本。
- `flights`：日期、航空公司、班號、起訖機場及起降時間。
- `days`：天次、日期、主要城市、景點、餐食及住宿。
- `notices`：小費、參團規範、交通、保險、護照簽證、特殊需求、房型、
  用藥、電壓及其他注意事項。
- `op_fields`：集合時間與地點、領隊姓名與電話、識別證、送機人員及
  緊急聯絡人；每欄均有值、來源與確認狀態。
- `weather`：行程日期、顯示城市、官方預報區、天氣、最高／最低溫、
  降雨機率、發布時間、取得時間、來源 URL 及可用狀態。
- `conflicts`：欄位、來源 A、來源 B、嚴重度、處理決定與決定者。
- `warnings`：不阻擋草稿或正式版，但必須呈現在審核報告的事項。
- `artifacts`：預期檔案、實際檔案、雜湊、檢查結果及使用的產生器版本。

任何可出現在 Word 或語音中的可變事實，都必須能回溯到來源或 OP 決定。

## 資料優先順序與衝突規則

來源優先順序固定如下：

1. OP 對該草稿明確確認的欄位值；
2. PDF 的日期、航班、天數、行程、餐食與飯店；
3. 官網的最新版「其他說明」；
4. 產生當下取得的官方短期天氣；
5. URL 單獨輸入時，官網可作為行程草稿來源。

只有 PDF 時，系統先從 PDF 擷取產品代碼並尋找唯一官網產品頁。找不到或找到
多個候選時，Word 仍可使用 PDF 內容建立草稿，但「官網其他說明」列為待確認；
不得把另一產品的說明當成相同內容。

下列差異為阻擋衝突：

- 出發日、回程日或行程天數；
- 去回程機場、班號、航班日期或起降時間；
- 每日主要住宿飯店或住宿城市；
- 天次對應的主要景點或行程順序。

阻擋衝突使狀態成為 `BLOCKED`。若仍能安全建立草稿，衝突欄位顯示黃色
「待 OP 確認」，語音不朗讀任何一方的爭議值；正式版一定停止。標點、簡稱、
全半形或不改變意思的餐食文字差異只列為提醒，並採 PDF 文字。

## OP 專屬欄位

下列欄位不得從行程內容推測：

- 集合時間與集合地點；
- 領隊姓名與行動電話；
- 識別證或行李牌資訊；
- 機場送機代表；
- 緊急聯絡人及電話；
- 尚未由 OP 確認的替代飯店。

草稿中缺少時，使用黃色底色及完整文字「待 OP 確認」。正式版不得保留任何
必要 OP 欄位的黃色狀態。

## 天氣來源與時效

第一階段以日本氣象廳（JMA）公開預報為唯一預設來源，不使用歷史平均值冒充
即時預報。實作透過官方公開頁面／PULL 資料取得：

- `VPFD51` 府縣短期天氣預報，用於今日至後天；
- `VPFW50` 府縣週間天氣預報，用於發布翌日至七日後。

重疊日期以較短期、較新發布的預報為準。住宿城市會映射到 JMA 的官方預報區，
輸出同時顯示旅客熟悉的城市名稱與實際採用的預報區。無法唯一映射時不猜測，
該日標示待確認。

每筆預報必須保存並顯示發布時間、實際取得時間、來源 URL 與來源署名。若行程
日期超出官方預報範圍，使用固定文字「尚無短期預報，請於出發前更新」。若
JMA 暫時無法讀取，也保留相同提醒並在審核報告另列讀取錯誤。

天氣只供一般行前參考。Word 與口語稿均提醒旅客，涉及人身安全或重大天候時，
仍應以日本氣象廳及相關主管機關最新警報為準。

## LIST Word 產生規則

產生器必須修改使用者已確認的 LIST 範本，不得以 `python-docx` 或其他工具重新
畫出一份外觀近似但結構不同的文件。

- 原始 `.doc` 以唯讀方式開啟，另存工作副本後再修改；來源永不覆蓋。
- 範本路徑由本機設定提供，範本本體不進 Git。
- 範本契約記錄必要表格、儲存格錨點、合併結構與 QR 圖片存在條件。
- 契約或版面指紋不符時立即停止，不猜測儲存格位置。
- 保留 A4 單頁、原有字型、框線、合併儲存格、QR Code 與固定文字。
- 依 5、6、7 天自動增減每日資料列，日期必須與天次一一對應。
- 先以固定優先規則縮短景點描述；仍溢出時停止正式產出，不把字縮到難以閱讀。
- 草稿檔名以 `DRAFT_` 開頭，必要缺漏欄位使用黃色「待 OP 確認」。
- 正式檔只有在狀態為 `CONFIRMED` 且版面驗證通過後才可產生。

每個 Word 都必須實際轉成 PDF／圖片做 QA，逐頁確認頁數、文字裁切、表格、QR、
合併儲存格與黃色欄位。PDF／圖片屬 QA 暫存物，不是預設交付品。

## 口語稿規則

口語稿只使用結構化資料，不直接把整頁 HTML 或 PDF 原文交給 TTS。固定順序為：

1. 產品名稱與出發日期；
2. 小費與團體規範；
3. 行程變動、車上座位及交通提醒；
4. 保險、安全與個人用藥；
5. 護照、簽證、行動不便及高齡旅客提醒；
6. 素食、房型與單人房差；
7. 電壓及每天主要住宿城市的可用天氣；
8. 以最終說明會資料與現場領隊指示為準的結尾。

口語化可以重整句子、刪除重複敘述及補上段落銜接，但不得改變金額、年齡、
人數、保險額度、限制或責任範圍。必要內容清單會逐項驗證小費、出團人數、
不可脫隊、行車時間、行程變更、座位、保險、護照效期、房型、素食、電壓及
天氣提醒是否出現。

目標長度為 6:00 至 8:00。系統合成後以實際音檔秒數判定；超出範圍時可依
固定壓縮／補充規則重新產生一次，第二次仍超出就保留草稿並列出警告，不以
大幅加速語音掩蓋內容長度問題。

## 語音與字幕

2026-08-09 的同稿人工試聽結果是 `Microsoft Yating` 明顯優於
`Microsoft Hanhan Desktop`。第一階段因此採完全本機的 Yating：

- 語系與聲音：Windows Media Speech 的 `Microsoft Yating`（`zh-TW`、女性）；
- 合成方式：整篇口語稿一次連續合成，不按字幕句子分成多個音檔；
- 韻律基準：先保留使用者通過之 Yating 預設韻律，不另行加速、裁切靜音或插入
  人工停頓；
- 輸出基準：保留引擎原生 PCM 16-bit 單聲道 WAV。已通過的短樣本為 16 kHz，
  實作仍須從實際 WAV header 驗證，不可只信任設定值；
- 發音調整：金額、日期、班號、機場代碼及日文地名必須經短樣本人工驗收後，
  才可加入明確、可測試的發音規則。

實機 probe 顯示 Yating 即使開啟 sentence／word boundary metadata，仍回傳零個
自動 marker；因此不得把該選項當成字幕契約。口語稿仍先依語意與手機可讀長度
建立 canonical 句段，再於第二句起的每個句段前插入唯一、零時長的 SSML
`<mark name="segment-NNN"/>`，把整份 SSML 只送入一次 TTS。實機已確認 Yating
會回傳 `Speech:Bookmark` marker，且插入 bookmarks 不改變同稿 WAV byte count。

1. `segment-002` 至最後一段的 bookmark 必須各自出現一次，名稱與順序完全相符；
2. marker 缺少、重複、未知、順序錯誤或時間不合法時，停止建立 SRT，不以平均
   字數或猜測時間補齊；
3. 第一段 SRT 從 `00:00:00,000` 開始；其結束時間及每個後續句段的開始時間，
   取自下一個／自己的 bookmark；最後一段以 WAV 實際 frame 數計算的結尾為準；
4. 所有 bookmark 時間必須嚴格遞增且位於 WAV 範圍內，最後一段必須精確覆蓋
   音檔結尾；
5. MP3 只由已驗證的主 WAV 轉檔，避免 MP3、WAV、SRT 三者內容或時間不一致。

Yating 是唯一自動選用的聲音。若目標 Windows 沒有 Yating、WinRT 合成逾時、
輸出不是可解碼 PCM WAV，或 bookmark 驗證失敗，系統保留 Word、TXT 與審核報告，
把音訊標示為未完成。不得自動退回 Hanhan，也不得自動建立或呼叫 Azure 資源。
Hanhan 只保留既有離線回歸與人工明確指定的技術比較用途，不是正式產出備援。

預設交付格式：

- MP3：單聲道、44.1 kHz、固定 128 kbps，供 LINE 手機播放；
- WAV：Yating 原生取樣率的 PCM 16-bit 單聲道，供未來嘴型同步；
- TXT：UTF-8 完整逐字稿；
- SRT：UTF-8，短句、最多兩行，保留橫式 16:9 字幕安全區的切句習慣；
- JSON／Markdown 製作資訊：聲音、引擎、產生時間、字數、秒數及來源。

本機 Yating 無法成功合成或 bookmark 驗證不通過時，仍交付 Word、逐字稿與錯誤報告；
不得建立猜測時間的 SRT，也不得宣稱語音完成。

## 狀態與審核

- `DRAFT_READY`：已建立可審核產出，沒有來源阻擋衝突，但仍可能有黃色 OP 欄位。
- `BLOCKED`：有阻擋衝突、來源無法唯一辨識或必要產生器失敗；可保留安全的部分
  草稿，但不能產生正式版。
- `CONFIRMED`：阻擋衝突及必要 OP 欄位均已解決，OP 對該 `draft_id` 明確確認，
  Word 與音訊 QA 也通過。

每次重新擷取來源、變更任何事實、更新天氣或修改口語稿後，都會產生新的
`draft_id`，舊確認不能自動沿用。

## 產出與資料保護

每次產出放在 Git 忽略的：

`output/briefings/<product-code>/<timestamp>/`

預期檔案包括：

- `DRAFT_<product-code>_說明會資料.docx`

## 失敗行為

- URL 不屬於允許的新魅力網域：停止，要求有效來源。
- PDF 無法讀取：保留 URL 流程；沒有 URL 則停止並回報頁面／檔案問題。
- 產品代碼對應零個或多個頁面：保留 PDF 草稿，官網內容標示待確認。
- 官網結構漂移：解析器契約失敗，不以空字串當成功。
- JMA 超出預報範圍或暫時失敗：使用固定更新提醒，不使用歷史平均值。
- Word 範本契約、Word COM、轉檔或單頁驗證失敗：不產生正式 Word。
- Yating 不存在：停止音訊產出，明確列出缺少的 `Microsoft Yating`，不自動退回
  Hanhan 或雲端聲音。
- Yating 合成或 bookmark 驗證失敗：交付其餘安全產出並把語音標示未完成。
- Yating 合成逾時或結果不明：先檢查既有 WAV／bookmark 產出，不盲目重送。
- 未知的外部服務結果：先查本機產出及服務狀態，不盲目重送。

## 測試策略

### 離線自動測試

- 使用合成且去識別的 HTML／PDF 文字結構，不提交完整官網回應或來源文件。
- 大阪、東北、北海道各至少一個案例。
- 5、6、7 天的每日列增減、日期推導及單頁限制。
- URL-only、PDF-only、URL+PDF 三種輸入。
- OP、PDF、官網及天氣的來源優先順序。
- 日期、航班、飯店、天數與行程衝突的阻擋行為。
- 缺漏 OP 欄位的黃色狀態，以及正式版不得殘留黃色欄位。
- 城市到 JMA 預報區的唯一映射、範圍外日期與 JMA 失敗。
- 必要口語內容清單、數字保真及字幕時間連續性。
- capability probe 能區分 Yating 可用、缺少及 probe 失敗，且不啟動實際合成。
- Yating bookmark 名稱、數量、順序及時間軸不符時 fail closed。
- Yating 不可用或合成失敗時不自動呼叫 Hanhan、Azure 或其他聲音。
- 來源、個資、金鑰、HTML、XML、DOCX、PDF、MP3、WAV 與 SRT 不被 Git 追蹤。

### 本機整合與人工檢查

- 使用三份已確認的私有 LIST 樣本，驗證範本契約及 5／6／7 天版面。
- 每份 Word 實際轉成圖片並逐頁查看 A4 單頁、QR、表格與文字裁切。
- MP3、WAV 實際解碼及播放；程式計算秒數、取樣率、聲道與檔案雜湊。
- 第一批 Yating 樣本由人工聆聽台灣用語、日文地名、班號、金額、速度與停頓，
  通過後才固定發音設定；2026-08-09 的合成短稿已通過聲音方向選擇，正式管線樣本
  仍須在 WAV／SRT 契約完成後再驗收一次。

### 選擇性網路測試

官網與 JMA 測試必須與離線測試分開，且只有在使用者允許網路時執行。測試不得
建立付費資源、呼叫雲端 TTS、傳 LINE 或發布任何檔案。

## 第一階段驗收標準

1. 大阪、東北、北海道各至少一份實際案例成功產出並人工檢查。
2. URL 或 PDF 可各自建立可用草稿；兩者並用時能保留來源證據。
3. 日期、航班、飯店或行程矛盾時，正式版確實被阻擋。
4. 5、6、7 天 Word 都維持既有 LIST 的 A4 單頁外觀、QR 與表格結構。
5. 黃色欄位、衝突報告、來源與取得時間完整；沒有任何猜測值。
6. MP3 能在 LINE 手機版播放，WAV、逐字稿與 SRT 內容一致，語音約 6 至 8 分鐘。
7. 天氣只使用仍有效的 JMA 短期／週間預報，範圍外內容明確要求出發前更新。
8. 完整離線測試通過；網路、Word 視覺與音訊人工檢查留下實際結果。
9. Git 追蹤內容不含來源文件、產出檔、旅客個資、秘密或完整外部回應。
